# Trace v4.6 Claim-Fact Provenance Design

## 背景

当前 v4.5 trace 已经完成单一 `trace.html`、结构化 `trace.json`、组件级 records、dataflow edges、Trace Health、LLM token/finish reason、MCP/skill/tool/context 的基础语义记录。

但最近一次 DeepSeek 实测暴露出一个核心问题：trace 已经能说明“发生了什么”，但还不能稳定说明“回答中的每一个结论分别依据了哪些具体事实”。对于后续离线根因归因模块来说，当前 `evidence.fact` 和 `response.output` 之间的关系仍然偏粗。

本轮 v4.6 的目标是把 trace 从“流程与证据清单”推进到“可消费的 claim-fact provenance”。opencode 仍然不做根因诊断，只记录更精确的语义事实和证据链。

## 目标

1. 将 `evidence.fact` 从泛化 summary 升级为结构化事实。
2. 将最终回答拆成 `response.claim`，让每个回答结论都能关联直接证据、上下文证据和执行证据。
3. 降低 Trace Health 噪声，区分正常生命周期收口和真正 trace 质量问题。
4. 让 compaction 触发条件、算法选择和压缩前后上下文变化可稳定验证。
5. 保持 `trace.html` 为唯一正式可视化入口，不恢复 `viewer.html`。

## 非目标

1. 不在 opencode 内做根因诊断、责任归因或质量结论。
2. 不删除 v4.5 关键字段；允许新增 v4.6 字段和 record type。
3. 不把超大文本直接塞回主 record；大文本继续通过 artifact 引用查看。
4. 不为了追求完整性重新打开 stream delta、token delta 等低语义插装点。

## 方案选择

采用方案 B：Trace v4.6 Claim-Fact Provenance 收敛。

该方案保持当前架构稳定，只在 trace writer、semantic contract、viewer、compaction 入口和测试中做增量改造。相比小修小补，它能解决离线归因最需要的 claim-fact 粒度问题；相比大重构，它不会破坏已有 release 和 benchmark 执行链路。

## 数据模型

### Evidence Fact v2

`evidence.fact` 在保留 v4.5 字段的基础上新增：

```ts
type StructuredClaim = {
  subject?: string
  predicate?: string
  value?: string | number | boolean | null
  qualifier?: string
  source_span?: {
    path?: string
    uri?: string
    line_start?: number
    line_end?: number
    snippet_preview?: string
  }
  extraction_method:
    | "explicit_structured_data"
    | "mcp_json_text"
    | "source_location_fields"
    | "verification_output"
    | "summary_sentence"
    | "fallback_summary"
  raw_artifact_ref?: string
}
```

抽取优先级：

1. `input.data.fact`、`input.data.claim`、`input.data.subject/predicate/value` 等显式结构化字段。
2. MCP 返回的 JSON 文本或 JSON-like 文本。
3. `path/file + symbol/name/key + line_start/line_end + snippet` 等代码定位字段。
4. verification/test/bash 输出中的命令、退出码、失败摘要。
5. summary 中可稳定识别的单句事实。
6. 无法解析时保留 fallback summary，并打质量标记。

新增质量标记：

```text
generic_claim
missing_source_span
fallback_summary_claim
unparsed_mcp_text
weak_verification_claim
artifact_only_claim
```

### Response Claim

新增正式 record type：`response.claim`。

```ts
type TraceResponseClaim = {
  claim_id: string
  response_segment_id?: string
  text: TraceFieldSummary
  claim_index: number
  direct_evidence_refs: string[]
  context_refs: string[]
  execution_refs: string[]
  source_locations?: TraceSourceLocation[]
  support_level: "direct" | "contextual" | "execution_only" | "unsupported" | string
  quality_flags: string[]
  metadata?: Record<string, unknown>
}
```

`response.output` 继续存在，代表完整输出；`response.claim` 表示其中可用于归因分析的最小结论单元。

回答拆分策略：

1. 按段落、列表项、句号、分号等切分。
2. 过滤纯寒暄、过渡语、无事实承载的短句。
3. 优先把所有 `direct_evidence_refs` 继承给每个 claim。
4. 如果未来调用点能传入 claim-level refs，则使用调用点传入的 refs。
5. 无直接证据的 claim 打 `unsupported_response_claim` 或 `context_only_claim`。

### Dataflow

新增 relation：

```text
claimed_by
supports_claim
contextualizes_claim
executed_for_claim
```

关系含义：

1. `response.output -> response.claim` 使用 `claimed_by`。
2. `evidence.fact -> response.claim` 使用 `supports_claim`。
3. `context.* -> response.claim` 使用 `contextualizes_claim`。
4. `tool.call`、`verification`、`change` 等执行记录到 claim 使用 `executed_for_claim`。

保留 v4.5 的 `supported_response`，但 v4.6 viewer 和离线消费应优先读取 claim-level edges。

### Trace Health v2

`metrics.trace_health` 新增：

```text
generic_evidence_facts
unsupported_response_claims
context_only_response_claims
unexpected_missing_close_records
expected_lifecycle_finalized_records
payload_duplication_groups
compaction_check_missing
```

降噪规则：

1. `run.start`、`llm.turn`、`agent.lifecycle` 等在 trace finish 被 finalizer 收口时，如果属于预期生命周期记录，标为 `expected_lifecycle_finalized`，不在问题列表中按 warning 展示。
2. 只有无法解释的 running record 才进入 `unexpected_missing_close_record`。
3. `response.output.source_refs` 过宽不再作为主要问题；如果 claim-level refs 完整，则只作为 info。

### Compaction Check

新增正式 record type：`context.compaction_check`，用于记录是否需要压缩以及为什么。

```ts
type TraceCompactionCheck = {
  check_id: string
  session_id?: string
  message_id?: string
  provider_id?: string
  model_id?: string
  token_usage?: TraceTokenUsage
  token_estimate?: number
  context_limit?: number
  reserved_tokens?: number
  overflow: boolean
  selected_algorithm?: string
  trigger_reason: string
  source_refs?: string[]
  metadata?: Record<string, unknown>
}
```

在 processor/prompt/compaction 路径上记录：

1. LLM step 结束后是否 overflow。
2. prompt 循环里为何创建 compaction task。
3. compaction process 选择了哪些 head/tail message。
4. 压缩成功、失败或 compact-again 的原因。

为 release 验证增加测试/benchmark 专用环境开关：

```text
OPENCODE_TRACE_FORCE_COMPACTION=1
```

该开关只影响 trace 验证场景，用于稳定触发 compaction 记录；默认不改变用户正常使用行为。

## Viewer 设计

`trace.html` 继续作为唯一入口。新增或调整这些区块：

1. `Claim Evidence Matrix`：以回答 claim 为行，展示 direct evidence、context、execution refs、support level 和质量标记。
2. `Evidence Facts`：优先展示 structured claim 的 subject/predicate/value/source span。
3. `Trace Health`：按 expected/info/warning/error 分组，避免 expected lifecycle 混进问题。
4. `Compaction Ledger`：展示 compaction check、selected algorithm、token/limit/reserved、retained/dropped ids。
5. `Artifacts`：减少重复 preview，强调 artifact 链接和 hash。

## 成功标准

1. `trace.json.trace_version === "4.6"`。
2. `trace.html` 只生成一个正式 HTML 文件。
3. 每个 final response 至少生成一个 `response.claim`。
4. 有直接证据的回答 claim 产生 `supports_claim` edge。
5. MCP 返回事实能生成非泛化 `structured_claim`。
6. 无法解析的事实被标记质量问题，而不是伪装成强事实。
7. compaction 未触发时也能看到 `context.compaction_check` 说明原因。
8. force compaction 场景能看到 `context.compaction` 和 ledger。
9. Trace Health 中 expected lifecycle 不再作为主要问题噪声。
