# Trace v4.1 Attribution Facts Design

## Goal

Trace v4.1 makes each benchmark case trace a reliable semantic facts layer for offline root-cause attribution. The trace runtime does not diagnose failures. It records what the agent saw, where each fact came from, how data moved through components, and which records the final answer depended on.

## Scope

This design refines the existing Trace Semantic Contract v4 implementation. It keeps the observable-opencode execution model and HTML viewer, but changes the formal trace bundle so attribution tools can consume it directly.

In scope:

- Make `trace.json` the formal v4.1 provenance trace.
- Move the legacy v1.3 summary to `legacy-trace.json`.
- Promote structured MCP facts and source locations.
- Preserve subagent child trace references even when output is artifact-backed.
- Distinguish final user answers from intermediate summaries and subagent outputs.
- Record concrete context compaction ledgers where available, and mark estimated ledgers explicitly.
- Remove or merge weak observation nodes that add no semantic value.
- Add request-level LLM facts useful for attribution.

Out of scope:

- Online root-cause diagnosis.
- Scoring or ranking suspected root causes.
- Large text inlining inside `trace.json`; large payloads remain artifact-backed.
- A full event-sourcing rewrite.

## Trace Bundle Contract

The primary files are:

- `trace.json`: v4.1 provenance trace.
- `legacy-trace.json`: old v1.3 summary for compatibility.
- `manifest.json`: v4.1 manifest and file map.
- `records.jsonl`: streaming provenance records.
- `raw-events.jsonl`: raw runtime events.
- `trace.html`: unified human viewer.
- `viewer.html`: compatibility redirect to `trace.html`.
- `partial/latest.json`: latest v4.1 partial snapshot.

`manifest.files` must expose `trace`, `legacy_trace`, `trace_html`, `records`, `raw_events`, `viewer_alias`, and `partial_latest`.

## Record Semantics

Every formal record keeps `record_id`, `component`, `event_type`, `timestamp`, `time_ms`, `title`, `status`, `source_refs`, `source_locations`, `artifact_refs`, and `data`.

Records should be meaningful by themselves:

- A low-level streaming delta is not a formal record.
- A record with no semantic content should be merged into its parent record.
- A retained low-value record must include `semantic_value: "low"` and a reason.

## MCP Facts

MCP tool outputs often return JSON as text. v4.1 attempts to parse text content safely. If an item contains `key`, `fact`, `path`, `line_start`, or `line_end`, the formal record includes:

```json
{
  "typed_resources": [
    {
      "type": "repo_fact",
      "key": "pricing-owner",
      "fact": "pricing.mjs owns coupon math...",
      "source_location": {
        "path": "src/pricing.mjs",
        "line_start": 1,
        "line_end": 20
      }
    }
  ],
  "source_locations": [
    {
      "path": "src/pricing.mjs",
      "line_start": 1,
      "line_end": 20
    }
  ]
}
```

The parser is best-effort and must not fail a trace if MCP content is not JSON.

## Subagent References

Each `subagent.call` record must include stable top-level linkage:

- `child_session_id`
- `child_trace_dir`
- `child_status`
- `output_artifact_id` when output is artifact-backed

This linkage must exist even when the full subagent output is summarized or stored in an artifact.

## Response Roles

`response.output` records include:

- `response_role`: `final_answer`, `intermediate_summary`, `subagent_result`, or `auto_continue_summary`
- `visibility`
- `turn_index`
- `is_final_for_case`

Only the final user-facing case answer is `is_final_for_case: true`. Subagent results, context summaries, and auto-continue summaries are not final answers.

## Context Compaction Ledger

`context.compaction` records include:

- `trigger`
- `algorithm`
- `input_tokens`
- `context_limit`
- `token_estimate_before`
- `token_estimate_after`
- `retained_message_ids`
- `dropped_message_ids`
- `retained_fact_refs`
- `dropped_fact_refs`
- `summary_artifact_id`
- `ledger_id_quality`: `concrete`, `estimated`, or `unknown`
- `auto_continue`

If real message IDs are unavailable, the record may keep estimates, but it must mark `ledger_id_quality: "estimated"`.

## LLM Request Facts

`llm.call` records should expose request-level facts when available:

- `request_id`
- `agent`
- `provider_id`
- `model_id`
- `message_count`
- `system_count`
- `tool_count`
- `token_usage`
- `cache_usage`
- `finish_reason` or `stop_reason`
- `input_context_snapshot_ref`

These facts allow offline attribution to compare model turns without parsing raw events.

## HTML Viewer

`trace.html` remains the only viewer. It should show:

- Component dataflow.
- Execution timeline.
- IO inspector with horizontally scrollable input/output panels.
- Context ledger.
- Response roles and final-answer markers.
- Typed resources and source locations.
- Artifact links for large text.

`viewer.html` remains a redirect alias only.

## Validation Criteria

The implementation is acceptable when:

- Unit tests verify the v4.1 file contract.
- Unit tests verify MCP typed resources and source locations.
- Unit tests verify subagent top-level child trace references.
- Unit tests verify final and non-final response roles.
- Unit tests verify compaction ledger quality.
- Unit tests verify weak observation suppression.
- A real trace run covers tool calls, MCP, skill, subagent, LLM calls, and compaction.
- Secret scanning finds no API key pattern in generated trace output.
