# Trace v4.8 Final Claim Gate + Evidence Match Calibration Design

## Background

Trace v4.7 improved evidence semantics and claim splitting, but the Loop 2 release traces exposed four attribution problems that reduce offline root-cause analysis precision:

- MCP JSON facts are sometimes parsed by line-pattern extraction before the structured JSON candidate wins, so the trace loses the stronger `mcp_json_text` provenance method.
- Intermediate assistant notes and forced-compaction summaries can be emitted as `response.claim` before final response normalization runs.
- Response-claim evidence matching is still too broad. Generic verification facts can be matched to owner or discount claims because only text overlap is considered.
- User-requested local skills may be mentioned in prompt/context, but skill discovery or load/miss status is not represented as a formal record.

## Goals

- Emit `response.claim` records only for the final user-visible answer.
- Preserve MCP JSON evidence as `mcp_json_text` when a JSON structured fact is available.
- Make claim-to-evidence matching more explainable and less over-attributed.
- Add a formal signal for requested skills and skill availability/miss so offline analysis can tell whether the agent ignored or could not load a skill.
- Keep `trace.html` as the single report surface.

## Contract Changes

- `trace_version`: `4.8`.
- `response.claim.data` adds:
  - `match_reasons?: string[]`
  - `candidate_evidence_refs?: string[]`
  - `original_direct_evidence_refs?: string[]`
- `trace_health` adds:
  - `non_final_response_claims`
  - `weak_evidence_matches`
  - `mcp_json_parse_shadowed`
  - `skill_request_unresolved`
- `skill.load` may be used for skill request facts even when no actual skill tool call happened. These records must clearly state whether the skill was `requested`, `available`, `loaded`, or `missing`.

## Design

### Final Claim Gate

Move automatic final-answer claim generation from `responseOutput()` to `finish()`:

1. `responseOutput()` records segments only.
2. `finish()` calls `normalizeFinalResponseSegments()`.
3. `finish()` calls a new `emitFinalResponseClaims()` that emits claims only for segments with:
   - `response_role === "final_answer"`
   - `visibility === "user_visible"`
   - `is_final_for_case === true`
4. The method is idempotent via a `claimedResponseSegmentIDs` set.

This prevents intermediate tool-progress text and compaction summaries from polluting the claim matrix.

### MCP JSON Priority

Structured JSON candidates with `subject`/`predicate`/`value` must beat line-pattern extraction. Candidate ranking:

1. `mcp_json_text` with subject/predicate/value.
2. Explicit structured data with subject/predicate/value.
3. Source-line pattern extraction.
4. Source location fallback.

If a line-pattern extraction would have happened but a stronger MCP JSON candidate wins, add `mcp_json_parse_shadowed` only as an internal quality diagnostic if needed. The preferred successful path should be `mcp_json_fact_extracted`.

### Evidence Match Calibration

The matcher should produce both a score and reasons:

- High confidence reasons:
  - exact structured value match
  - subject match
  - predicate/semantic synonym match
  - source path or line match
  - verification status match for test-result claims
- Verification facts should not support owner/design/file-location claims unless the claim mentions tests, passed/failed status, assertion values, or command output.
- Maximum matched direct evidence refs defaults to 3.
- `weak_evidence_match` is set when a claim is direct only because of low-quality generic overlap.

### Skill Request Record

Detect explicit user requests of the form `use <name> skill`, `<name> skill`, or Chinese equivalents in prompt text. At prompt assembly time, emit a formal `skill.load` node:

- `skill_name`
- `request_source: "user_prompt"`
- `status: "requested" | "missing" | "loaded"`
- `available_skill_names`
- `source_refs`

The current implementation can conservatively mark a requested skill as `missing` when it is not in the available skills list captured in model-message system context and no skill tool call record exists.

## Success Criteria

- v4.8 release traces contain no `response.claim` whose parent response segment is not final.
- MCP `repo_fact` evidence for `quote-owner` is `extraction_method: "mcp_json_text"` and contains `renewalQuote/owner/billing-platform`.
- Final claim matrix in forced-compaction case contains only the final answer claims, not the compaction summary checklist.
- Owner/discount claims do not match verification-output facts unless the claim itself discusses test result or assertion output.
- `trace_health.non_final_response_claims === 0` for normal successful cases.
- If a requested local skill is not visible to the agent, trace records a `skill.load` missing/requested fact instead of leaving it implicit.
