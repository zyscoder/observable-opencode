# Trace v4.2 Viewer And Facts Design

## Background

Trace v4.1 turned `trace.json` into the formal provenance facts layer and kept `trace.html` as the human-readable report. Real release-binary validation exposed five gaps:

- New cases still generate both `trace.html` and `viewer.html`, even though the expected product surface is a single HTML report.
- The current `trace.html` is visually less useful than the previous flow/table-oriented report because it reads like repeated JSON cards.
- `metrics.token_usage` can serialize as `"[Circular]"`, and `llm.call` records often lack structured token usage.
- `subagent.call.data.child_trace_dir` can point at a directory that is not actually produced.
- Loop continuation and compaction can keep running after a user-visible answer, but the trace does not explain the loop decision clearly enough.

## Goals

Trace v4.2 must make each case trace easier for two consumers:

- A developer opening `trace.html` should quickly understand what the agent did, which components exchanged data, where important facts came from, and where the run went wrong.
- An offline attribution module should consume `trace.json` as a structured fact layer without relying on visual-only inference.

Trace v4.2 still must not diagnose root causes by itself. It records facts only.

## Output Contract

Each new traced case writes exactly one HTML report:

- `trace.html`: the only visualization entry point.

Each new traced case still writes these JSON/text artifacts:

- `manifest.json`
- `trace.json`
- `legacy-trace.json`
- `provenance-trace.json`
- `records.jsonl`
- `raw-events.jsonl`
- `partial/latest.json`
- `artifacts/sha256/*`

`viewer.html` is removed from new output. `manifest.files.viewer_alias` is removed. Documentation must not instruct users to open `viewer.html`.

## Formal Trace Changes

### Token Usage

`manifest.token_usage`, `trace.metrics.token_usage`, and each `llm.call` record must use JSON-safe token usage objects. They must never contain `"[Circular]"`.

`llm.call` records should preserve:

- `agent`
- `provider_id`
- `model_id`
- `message_count`
- `system_count`
- `tool_count`
- `finish_reason`
- `stop_reason`
- `cache_usage`
- `token_usage`

### MCP Facts

When an MCP call returns JSON text with repo facts, both records must expose the parsed facts:

- the `mcp.call` record
- the related MCP `observation` record

The parsed facts must appear as:

- `typed_resources`
- `source_locations`

### Subagent Trace References

Subagent records must never point at a fake child trace directory.

If a child trace directory exists, the record includes:

- `child_trace_available: true`
- `child_trace_dir`
- `trace_ref.child_trace_dir`

If it does not exist, the record includes:

- `child_trace_available: false`
- `child_session_id`
- no `child_trace_dir`
- no `trace_ref.child_trace_dir`

The subagent output artifact reference remains available through `output_artifact_id`.

### Loop Decisions

Each agent loop continuation decision should create a formal `loop.decision` record with:

- `decision`: `continue`, `stop`, `auto_continue`, or `unknown`
- `reason`
- `agent`
- `message_id`
- `part_count`
- `part_types`
- `has_user_visible_response`
- `has_final_answer`
- `synthetic_continue`
- `compaction_continue`

This record records the loop fact; it does not judge whether the loop was correct.

### Runtime Metadata

Low-value runtime fields such as `sessionID`, `messageID`, `part_count`, and `part_types` should be grouped under `runtime_refs` or loop-specific semantic fields instead of being spread through primary data sections. `raw-events.jsonl` remains the place for raw runtime payloads.

## HTML Design

The report should return to a more readable flow/table style while preserving v4.2 facts.

### Sections

1. Overview
   - case id, status, duration, records, edges, artifacts, token totals
   - no giant raw JSON block

2. Agent Flow
   - chronological flow of `task.loop`, `loop.decision`, `llm.call`, `tool.call`, `mcp.call`, `skill.load`, `subagent.call`, `context.compaction`, and `response.output`
   - compact event cards with status, duration, token usage, and response role

3. Component Dataflow
   - table of normalized dataflow edges
   - readable labels and component/source/target columns

4. IO Inspector
   - two-column layout with Input and Output
   - each side scrolls horizontally and vertically
   - values prefer previews with artifact links for full content

5. Semantic Facts
   - typed resources
   - source locations
   - verification parsed failures
   - response roles and final-answer marker

6. Context And Compaction
   - context packages
   - compaction ledger quality
   - retained/dropped ids or estimated markers
   - summary artifact links

7. Artifacts
   - artifact id, label, length, occurrence count, and relative path

### Visual Style

Use the previous viewer's clearer workbench feel:

- dense but readable tables
- compact flow rows
- restrained colors
- no decorative cards
- no oversized hero treatment
- no nested cards
- horizontal scrolling for long input/output payloads

## Documentation Updates

`docs/observable-benchmark-trace.md` must describe:

- `trace.html` as the only HTML report
- no `viewer.html`
- v4.2 trace semantics
- token usage and subagent trace availability rules

## Acceptance Criteria

- Focused observability tests pass.
- Typecheck passes.
- New trace output contains `trace.html` and does not contain `viewer.html`.
- `manifest.files.viewer_alias` is absent.
- `trace.metrics.token_usage` is an object, not `"[Circular]"`.
- `llm.call` records include structured token usage when usage is available.
- MCP repo facts appear on `mcp.call` and MCP observation records.
- Subagent records do not expose nonexistent child trace directories.
- At least one `loop.decision` record is present when loop events are observed.
- `trace.html` renders flow, dataflow, IO, semantic facts, context, and artifacts sections.
