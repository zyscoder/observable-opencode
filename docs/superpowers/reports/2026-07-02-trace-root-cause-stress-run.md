## Purpose

This run validates whether the current observable trace is useful as evidence for a downstream, offline root-cause diagnosis module. The benchmark cases intentionally contain difficult failure modes: wrong implementation target, conflicting evidence, MCP evidence ignored, context compaction risk, subagent summary trust, insufficient verification, tool failure handling, and design quality regression.

The goal is not to perform root-cause diagnosis inside observable-opencode. The goal is to check whether trace data preserves enough semantic facts, provenance, and dataflow edges for another module to diagnose root causes later.

## What Worked

The current trace already captures several high-value semantic layers:

- Prompt assembly and persisted user message records.
- Context transform snapshots before plugin transform, after plugin transform, and before LLM request.
- LLM call records with provider, model, message count, system prompt count, and tool count.
- Tool calls with structured input, output previews, duration, path metadata, and change/verification extraction.
- Dataflow edges connecting prompt, context, LLM, decisions, tool calls, changes, verification, and response claims.
- Semantic facts extracted from tool outputs and response text.
- Response claims with direct evidence refs, candidate evidence refs, execution refs, support level, match strategy, and match score.
- MCP calls and MCP result consumption in the `ignored-mcp-fact` case.
- Subagent call presence and parent consumption in the `subagent-misleading-summary` case.
- Compaction checks and context packages in the `compaction-lost-constraint` case.

These records are enough to support many offline questions, such as:

- Did the agent read the relevant file before editing?
- Which evidence facts supported the final claim?
- Did the final answer cite the modified file, the requirement source, and verification output?
- Which files changed and which command verified the change?
- Did a child agent run, and did the parent use its output?

## Missing Or Weak Semantics

### 1. Tool failure semantics are ambiguous

In `tool-failure-hallucination`, the required `unsupported_claims` evidence is missing and the trace only reaches `partial`.

More importantly, the failed read of `docs/current-requirement.md` is represented as a long-running `tool.call` finalized as `cancelled/finalized_without_close` after the server process stops. That blurs three different cases:

- The tool actually failed because the file did not exist.
- The tool was still running when the trace was finalized.
- The case was already complete and the HTTP server was intentionally stopped.

For root-cause analysis, these must be separate semantic states. A downstream module should be able to tell whether the model observed a tool failure, ignored it, recovered by searching alternatives, or hallucinated despite missing evidence.

Recommended change: add first-class `tool.result` / `tool.error` semantic records with `call_id`, `tool_name`, `error_kind`, `exit_status`, `observed_by_model`, `recovered_by_followup_action`, and `downstream_claim_refs`.

### 2. Unsupported claim detection is still too weak

The current claim attribution marks final response claims with evidence refs, but it does not reliably emit a separate "unsupported or weakly supported claim" semantic record.

This matters when a final answer says something that is only indirectly supported by context or by a failed tool path. The downstream analyzer needs explicit claim-quality facts, not just a large candidate evidence list.

Recommended change: add a `claim.support_assessment` record per final response claim with `support_level`, `missing_evidence_types`, `contradicting_evidence_refs`, `weak_match_reasons`, and `tool_failure_dependency_refs`.

### 3. Lifecycle finalization creates false cancellation noise

All cases contain `run.start` and multiple `agent.lifecycle/turn.started` records finalized as `cancelled` when the HTTP server is stopped after the case completes. This is operationally understandable but semantically noisy.

For diagnosis, "case completed and server stopped" should not look like "agent turn was interrupted." Otherwise an offline analyzer may over-rank cancellation as a root cause.

Recommended change: add an explicit `case.completed` / `session.completed` lifecycle record and finalize still-open server/session spans with `status=closed_after_case_completion` or `status=service_shutdown_after_completion`, not generic `cancelled`.

### 4. Raw stream events remain too large for diagnosis

`raw-events.jsonl` still contains thousands of low-level provider stream events, including many `stream.tool-input-delta` fragments. They are useful for lossless replay, but they are not useful in the semantic trace view or normal offline diagnosis.

Recommended change: keep raw stream deltas only in raw artifacts, and ensure `trace.json` / `trace.html` prioritize assembled `tool.input`, `tool.result`, `llm.turn`, `response.output`, and semantic facts. Add aggregate counts for omitted stream fragments so debugging is still possible.

### 5. Some design records are over-extracted

The stress run shows `design_record` extraction from short progress messages such as "found docs/architecture.md". These are not real designs and can pollute downstream analysis of design quality.

Recommended change: gate `design_record` extraction by response role, length, and structural cues. Prefer only final answers or explicit design/planning sections unless the text contains clear design dimensions like requirement summary, constraints, selected option, tradeoffs, and test strategy.

## Redundant Or Bloated Information

The following data is useful as artifact-level evidence, but too noisy if treated as primary semantic nodes:

- Full tool schema snapshots repeated across turns.
- Large provider request snapshots repeated in both context records and artifacts.
- Repeated broad response refs that attach many context/evidence refs to every claim.
- Lifecycle `turn.started` records left open until process shutdown.
- Token-level or fragment-level stream deltas.

Recommended policy:

- Keep heavy data as content-addressed artifacts.
- Use trace nodes for stable semantic summaries and refs.
- Mark raw-only events as `debug/raw` so they do not appear as root-cause candidates by default.

## Next Improvement Proposal

The next trace iteration should focus on "failure and support semantics" rather than adding more generic nodes:

1. Add explicit tool error/result records and distinguish observed tool errors from trace finalization artifacts.
2. Add claim support assessment records, including unsupported/weak/contradicted claims.
3. Add session/case lifecycle close semantics for HTTP-server-based benchmark execution.
4. Tighten design record extraction to avoid creating design facts from short progress messages.
5. Update the stress-case analyzer to fail when cancelled lifecycle noise appears without a matching completed-session record.

This would make the trace more reliable as an evidence substrate for offline causal diagnosis without putting the diagnosis logic inside observable-opencode.
